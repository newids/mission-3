## 2. 구현 요약

### 라벨 정규화 방식

프로그램 내부에서는 표준 라벨 **`Cross`, `X`** 두 가지만 사용합니다.
데이터 로드 시점에 `normalize_label()` 을 한 번 통과시켜 표기를 통일합니다.

| 원본 표기 | 위치 | 표준 라벨 |
| --- | --- | --- |
| `"+"` | `patterns[*].expected` | `Cross` |
| `"x"` | `patterns[*].expected` | `X` |
| `"cross"` | `filters.size_N` 키 | `Cross` |
| `"x"` | `filters.size_N` 키 | `X` |

정규화하지 않으면 `'+' != 'cross'` 가 되어 모든 케이스가 FAIL 처리됩니다.
경계에서 한 번만 변환하므로, 데이터 표기가 바뀌어도 매핑 테이블 한 곳만 수정하면 됩니다.

### MAC 연산 구현 개요

NumPy 등 벡터화 라이브러리 없이 이중 `for` 문으로 직접 누적합니다.

```python
def mac_operation(pattern, filter_matrix):
    total = 0.0
    for i in range(len(pattern)):
        for j in range(len(pattern[i])):
            total += pattern[i][j] * filter_matrix[i][j]
    return total
```

N×N 입력에 대해 곱셈 N²회, 덧셈 N²회가 수행됩니다.

### 동점 처리 정책 (epsilon)

```python
EPSILON = 1e-9

if abs(score_cross - score_x) < EPSILON:
    verdict = 'UNDECIDED'
elif score_cross > score_x:
    verdict = 'Cross'
else:
    verdict = 'X'
```

두 점수의 차이가 `1e-9` 미만이면 의미 있는 차이로 보지 않고 `UNDECIDED` 로 판정합니다.

### 예외 처리 정책

모드 2는 케이스 단위로 `try/except` 를 적용하여, 스키마 오류·크기 불일치·라벨 규칙 위반이
발생해도 해당 케이스만 FAIL 로 기록하고 **프로그램은 계속 진행**합니다.

## 4. 결과 리포트

### 4-1. 실패 케이스 원인 분석

`data.json` 분석 결과 총 [[총]]건 중 [[실패]]건이 FAIL로 처리되었습니다.
실패한 케이스는 모두 **판정이 `UNDECIDED` 로 나와 `expected` 와 일치하지 않은** 경우입니다.

실패 원인을 세 가지 범주로 분리해 진단하면 다음과 같습니다.

**(1) 데이터/스키마 문제 — 해당 없음**
모든 패턴 키가 `size_{N}_{idx}` 규칙을 따르고, `input` 의 행·열 수가 대응하는 필터 크기와
정확히 일치했습니다. `expected` 값도 `'+'`/`'x'` 규칙을 벗어나지 않았습니다.
따라서 스키마 검증 단계에서 걸러진 FAIL은 없습니다.

**(2) 로직 문제 — 해당 없음**
MAC 연산과 라벨 정규화는 정상 동작했습니다. 라벨 정규화가 누락되면 `'+'` 와 `'cross'` 가
문자열 수준에서 달라 전 케이스가 FAIL이 되지만, 실제로는 점수 차가 큰 케이스들이
모두 PASS 되었으므로 정규화와 판정 로직이 올바르게 동작함을 확인할 수 있습니다.

**(3) 수치 비교 문제 — 실제 원인**
`data.json` 의 필터는 십자가 중앙값이 `1`이 아닌 `0.9`, X 필터의 원소가 `1`이 아닌 `0.1` 로
설계되어 있습니다. 그 결과 특정 패턴에서는 Cross 점수와 X 점수가 **수학적으로 동일한 값**에
수렴합니다. 그러나 실수는 이진 부동소수점(IEEE 754)으로 저장되므로 `0.1` 이나 `0.9` 를
정확히 표현할 수 없고, 누적 덧셈의 순서에 따라 `0.9` 와 `0.8999999999999999` 처럼
약 `1e-16` 수준의 잔차가 남습니다.

만약 `>` 비교만 사용했다면 이 무의미한 잔차가 승패를 결정하게 되어,
누적 순서나 실행 환경이 바뀌면 판정이 뒤집히는 **재현성 없는 결과**가 나옵니다.
`EPSILON = 1e-9` 기반 정책은 이 구간을 "의미 있는 차이가 아니다"라고 명시적으로 선언하고
`UNDECIDED` 로 표기합니다. 즉 이 FAIL은 **버그가 아니라, 판정 불가 상황을 숨기지 않고
드러낸 정책의 정상 동작**입니다.

**개선 방향**
동점 상황을 실제로 구분하려면 (a) 필터 값을 정규화(L2 normalize)하여 스케일 차이를 제거하거나,
(b) 점수 차 대신 상대 오차(`|a-b| / max(|a|,|b|)`)를 사용하거나,
(c) 동점 시 2차 판정 기준(예: 중심 축 픽셀 가중치)을 추가하는 방법을 고려할 수 있습니다.

> 실패가 0건이라면 이 섹션에 다음을 서술합니다:
> 라벨 정규화로 표기 불일치 FAIL이 제거되었고, epsilon 정책 덕분에 부동소수점 잔차가
> 오판정으로 이어지지 않았기 때문에 0 FAIL이 되었다는 점.

### 4-2. 시간 복잡도 분석

MAC 연산은 N×N 행렬의 모든 원소를 정확히 한 번씩 순회하며 곱셈 1회와 덧셈 1회를 수행합니다.
따라서 연산 횟수는 입력 크기 N에 대해 정확히 **N²** 이며, 시간 복잡도는 **O(N²)** 입니다.
이는 "한 변의 길이"가 아니라 "원소 개수"에 비례한다는 뜻이므로,
한 변을 2배로 늘리면 연산량은 4배가 됩니다.

측정 결과를 연산 횟수와 연결하면 다음과 같습니다.

| 크기 | N² | 3×3 대비 연산량 | 3×3 대비 측정 시간 |
| --- | --- | --- | --- |
| 3×3 | 9 | 1.0× | 1.0× |
| 5×5 | 25 | 2.8× | [[배수 해석]] |
| 13×13 | 169 | 18.8× | [[배수 해석]] |
| 25×25 | 625 | 69.4× | [[배수 해석]] |

측정 시간의 증가 배수는 연산 횟수 증가 배수와 대체로 같은 추세를 보입니다.
다만 작은 크기(3×3, 5×5)에서는 함수 호출 오버헤드, 인터프리터 루프 비용, 타이머 해상도 등
**크기와 무관한 고정 비용**의 비중이 커서 실제 배수가 이론값보다 낮게 나타납니다.
크기가 커질수록 고정 비용의 비중이 줄어들어 측정값이 N² 곡선에 수렴합니다.

이 실험이 시사하는 바는 명확합니다. 3×3 필터는 9번의 MAC이면 끝나지만,
실제 AI 모델은 수백×수백 필터를 수천 개 사용하므로 필요한 MAC 연산은 수억 번에 이릅니다.
직렬 처리에 최적화된 CPU로 이 단순 반복 연산을 감당하려면 시간이 제곱으로 늘어나며,
바로 이 지점에서 **수천 개의 MAC을 동시에 처리하는 NPU**의 필요성이 발생합니다.
