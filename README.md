# Mission 3 — Mini NPU Simulator

AI가 계산하는 방식(MAC 연산)을 흉내 내는 작은 계산기.
입력 패턴이 **Cross(십자가)** 필터와 **X** 필터 중 어느 쪽에 더 가까운지를
외부 라이브러리 없이 순수 Python 반복문으로 판정하는 콘솔 애플리케이션입니다.

- 미션 명세: [docs/MISSION-3.md](docs/MISSION-3.md)
- 사전 분석·개념 자료: [_workplace/](_workplace/)

## 1. 실행 방법

```bash
python main.py                # data.json은 main.py와 같은 폴더에서 자동 탐색
python main.py 경로/data.json  # 다른 경로의 데이터 파일 지정 (선택)
```

- 요구 환경: **Python 3.8 이상**, 외부 라이브러리 불필요 (표준 라이브러리 `json`, `time`, `sys`, `os`만 사용)
- 실행하면 모드 선택 메뉴가 나온다:

| 선택 | 모드 | 동작 |
| :---: | --- | --- |
| `1` | 사용자 입력 (3×3) | 필터 A·B와 패턴을 한 줄씩(공백 구분) 입력 → 점수/연산 시간/판정 출력 → 3×3 성능 분석 |
| `2` | data.json 분석 | 필터 로드 → 케이스별 판정·PASS/FAIL → 성능 분석(3×3~25×25) → 결과 요약 |
| `3` | 패턴 생성기 (보너스) | 크기 N 입력 → N×N Cross/X 패턴 자동 생성 및 검증 |

모드 1 입력 예시 (십자가 필터 A, X 필터 B, X 패턴):

```text
선택: 1
필터 A (3줄 입력, 공백 구분)
0 1 0
1 1 1
0 1 0
필터 B (3줄 입력, 공백 구분)
1 0 1
0 1 0
1 0 1
패턴 (3줄 입력, 공백 구분)
1 0 1
0 1 0
1 0 1
→ A 점수: 1.0 / B 점수: 5.0 / 판정: B
```

행·열 개수가 틀리거나(`1 2`) 숫자가 아닌 값(`1 a 0`)을 입력하면
안내 문구를 출력하고 해당 행부터 재입력을 유도한다. 프로그램은 종료되지 않는다.

## 2. 구현 요약

### 데이터 구조

`Grid` 클래스가 n×n 2차원 패턴/필터를 저장하며 `get(i, j)` / `set(i, j, v)`로
위치별 읽기/쓰기를 제공한다. `Grid.from_rows()`가 JSON 배열을 받아
**정사각형 여부·숫자 타입을 검증**하므로 스키마 검증이 한곳에 모인다.
3×3, 5×5, 13×13, 25×25를 포함한 임의 크기를 처리한다.

### MAC 연산 (외부 라이브러리 금지 준수)

```python
def mac(pattern_rows, filter_rows):
    total = 0.0
    n = len(pattern_rows)
    for i in range(n):
        row_p = pattern_rows[i]
        row_f = filter_rows[i]
        for j in range(n):
            total += row_p[j] * row_f[j]   # Multiply → Accumulate
    return total
```

이중 for 루프가 정확히 N² 번 돌며, 같은 위치끼리 곱해(Multiply) 누적(Accumulate)한다.
보너스로 2차원 배열을 길이 N²의 1차원 배열로 평탄화한 `mac_flat()`도 구현해 성능을 비교했다.

### 라벨 정규화

내부 표준 라벨은 `Cross`, `X` 두 가지뿐이다. `normalize_label()`이
외부 표기를 비교 직전에 표준형으로 모은다:

| 외부 표기 | 출처 | → 표준 라벨 |
| --- | --- | --- |
| `'cross'` | filters 키 | `Cross` |
| `'+'` | expected 값 | `Cross` |
| `'x'` | filters 키 / expected 값 | `X` |

콘솔 출력과 PASS/FAIL 비교는 전부 표준 라벨 기준으로 수행한다.
해석 불가능한 라벨(예: `'triangle'`)은 해당 케이스만 FAIL 처리한다.

### 점수 비교 정책 (epsilon)

```python
EPSILON = 1e-9
if abs(score_cross - score_x) < EPSILON:  # 동점 → UNDECIDED
```

부동소수점 누적합은 더하는 순서에 따라 최하위 비트가 흔들리므로 `==`/`>` 단순 비교는
노이즈로 판정하는 셈이 된다. 차이가 `1e-9` 미만이면 동점(UNDECIDED)으로 간주하고,
UNDECIDED는 expected와 결코 같을 수 없으므로 항상 FAIL로 집계한다.

### 오류 처리 (모드 2가 절대 중단되지 않는 이유)

케이스마다 ① 키 형식(`size_{N}_{idx}`) → ② 해당 크기 필터 존재 → ③ 배열 정사각형/숫자
→ ④ 필터·패턴 크기 일치 → ⑤ expected 라벨 순으로 검증하고,
어느 단계에서 실패해도 **해당 케이스만 FAIL + 원인 메시지**를 남기고 다음 케이스로 진행한다.

## 3. 결과 리포트

### 3-1. 실행 결과 요약 (모드 2, 제공된 data.json)

```text
총 테스트: 6개 / 통과: 3개 / 실패: 3개

실패 케이스:
- size_5_1 : 동점(UNDECIDED) 처리 규칙에 따라 FAIL (|차이| = 1.11e-16 < 1e-09)
- size_13_2: 동점(UNDECIDED) 처리 규칙에 따라 FAIL (|차이| = 2.66e-15 < 1e-09)
- size_25_1: 동점(UNDECIDED) 처리 규칙에 따라 FAIL (|차이| = 1.78e-15 < 1e-09)
```

| 케이스 | Cross 점수 | X 점수 | 판정 | expected | 결과 |
| --- | --- | --- | --- | --- | --- |
| size_5_1 | 0.9 | 0.8999999999999999 | UNDECIDED | X | FAIL |
| size_5_2 | 8.9 | 0.1 | Cross | Cross | PASS |
| size_13_1 | 0.3 | 14.700000000000008 | X | X | PASS |
| size_13_2 | 7.499999999999997 | 7.5 | UNDECIDED | Cross | FAIL |
| size_25_1 | 4.9 | 4.899999999999999 | UNDECIDED | X | FAIL |
| size_25_2 | 52.9 | 0.1 | Cross | Cross | PASS |

### 3-2. 실패 원인 분석

이 3건의 FAIL은 프로그램 버그가 아니라 **데이터 설계에 내재된 수학적 동점**이다.
미션이 요구하는 3분류(데이터/스키마 vs 로직 vs 수치 비교)로 진단하면 다음과 같다.

1. **로직 문제인가? — 아니다.** 세 케이스를 반올림 오차 없는 정확 합산(`math.fsum`)으로
   재계산하면 두 필터의 점수가 **완전히 같은 값**이 된다 (예: size_5_1은 정확히 0.9 vs 0.9).
   즉 MAC 구현은 수학적으로 정확하다.
2. **수치 비교 문제인가? — 증상일 뿐이다.** epsilon을 제거하고 단순 대소 비교를 해도
   같은 3건이 실패한다(우열이 1e-16 규모의 반올림 노이즈로 결정되어 오답이 됨).
   epsilon 정책은 실패 개수를 바꾸지 않고, "노이즈에 의한 우연한 판정"을
   "동점이라 판정 불가"라는 **진단 가능한 신고**로 바꿔 준다.
3. **데이터/스키마 문제인가? — 그렇다. 이것이 근본 원인이다.** 제공된 필터는
   한 필터의 중앙 가중치가 상대 필터의 총합과 정확히 일치하도록 설계되어 있다
   (5×5: cross 중앙 0.9 = x 총합 0.9, 13×13: x 중앙 7.5 = cross 총합 7.5,
   25×25: cross 중앙 4.9 = x 총합 4.9). Cross 패턴과 X 패턴은 중앙 한 칸에서만
   겹치므로, "정답 필터의 전체 점수"와 "오답 필터의 중앙 한 칸 점수"가 정확히 같아진다.
4. 그 결과 각 크기마다 **스케일이 작게 눌린 필터가 정답인 케이스 1건씩**이 동점이 되어,
   원시 MAC 점수만으로는 원리적으로 구분이 불가능하다.
5. **개선안(검증 완료):** 점수를 필터·패턴의 L2 노름으로 나눠 정규화(코사인 유사도)하면
   스케일 차이가 상쇄되어 6/6 전 케이스가 PASS 한다 (예: size_5_1이 0.1011 vs 1.0000으로
   압도적 차이로 갈림). 다만 미션의 기본 요구사항은 "원시 MAC + epsilon 비교"이므로
   기본 판정 로직은 그대로 두고 개선안은 분석으로만 제시한다.
6. **교훈:** 스케일(총합·노름)이 다른 필터끼리 원시 MAC 점수를 직접 비교하면 안 된다.
   실제 CNN이 배치 정규화·가중치 정규화를 쓰는 이유와 정확히 같은 문제다.

### 3-3. 성능 분석과 시간 복잡도 O(N²)

측정 방법: I/O를 제외하고 `mac()` 함수 호출 구간만 `time.perf_counter()`로
**10회 반복 측정 후 평균**(워밍업 1회 별도). 실측치는 기기·실행마다 다소 달라진다.

| 크기 | 평균 시간(ms) | 연산 횟수(N²) | 이전 크기 대비 |
| --- | ---: | ---: | --- |
| 3×3 | 0.0019 | 9 | — |
| 5×5 | 0.0035 | 25 | 연산 2.8배 / 시간 1.8배 |
| 13×13 | 0.0162 | 169 | 연산 6.8배 / 시간 4.6배 |
| 25×25 | 0.0534 | 625 | 연산 3.7배 / 시간 3.3배 |

- MAC 1회는 N×N 모든 칸을 정확히 한 번씩 곱-누적하므로 연산 횟수는 정의상 N².
  실측에서도 N이 커질수록 시간 증가율이 연산 횟수 증가율에 수렴한다
  (13×13→25×25에서 연산 3.70배, 시간 약 3.3배). **시간 복잡도는 O(N²)** 다.
- 작은 N(3×3, 5×5)에서는 함수 호출·루프 초기화 같은 고정 오버헤드가 지배적이라
  비례가 다소 무너진다. 이것이 미션이 "10회 이상 반복 측정 후 평균"을 요구하는 이유다
  — 1회 측정은 오버헤드와 타이머 노이즈에 잠식된다.
- 25×25 한 장에 0.05ms 수준이지만, 실제 AI가 쓰는 수백×수백 필터 수천 개라면
  N² 스케일링 때문에 수억 번의 MAC이 필요해진다. 이 단순 반복 연산을
  병렬로 동시 처리하는 것이 NPU의 존재 이유다.

### 3-4. 보너스 — 1D 평탄화 최적화 비교 (B1)

2차원 배열을 길이 N²의 1차원 배열로 평탄화한 `mac_flat()`을 동일 입력·동일 10회
반복으로 비교했다. 본 실행 환경(CPython)에서는 전 구간에서 1D가 소폭 빨랐다
(예: 3×3 0.0019→0.0011ms, 25×25 0.0534→0.0503ms). 다만 이득 폭은 N이 커질수록
줄어드는데, CPython의 병목은 메모리 접근이 아니라 바이트코드 인터프리터 오버헤드이고
2D 버전도 행 참조를 지역 변수로 끌어와 내부 루프 비용을 이미 최소화했기 때문이다.
C/하드웨어처럼 캐시 지역성이 병목인 환경에서 1D 평탄화의 이득이 훨씬 커진다.
결과 표는 프로그램의 성능 분석 섹션에서 함께 출력된다.
