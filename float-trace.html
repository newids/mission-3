Codyssey Mission 3 · size_5_1 사건 기록

0.1을 아홉 번 더하면
0.9 0.8999999999999999

Mini NPU Simulator의 size_5_1 케이스가 UNDECIDED로 FAIL한 진짜 이유 — 컴퓨터가 소수를 다루는 방식을 요약, 애니메이션, 추적 스크립트, 실측 로그로 정리했음. (수치는 전부 Python 3.9.6 실측값)

1.요약 설명

한 문장으로: 0.1은 2진수로 저장할 수 없는 수라서, 저장할 때 한 번·더할 때마다 또 한 번 반올림되며 생긴 오차가 마지막에 한 눈금(1 ULP) 아래로 착지한 것.

  1. size_5_1의 X 점수는 대각선 9칸 × 0.1의 곱-누적, 즉 0.1을 9번 더한 값.
  2. 0.1은 2진수로 0.000110011001100… 무한 반복 소수라 정확히 표현 불가. float(IEEE 754)은 53비트에서 반올림해 0.1보다 +5.55×10⁻¹⁸ 큰 값을 저장.
  3. float 덧셈은 매번 결과를 다시 53비트로 반올림. 누적 오차가 +로 부풀다(3단계 +4.44×10⁻¹⁷) 0.5에서 정확히 0이 되고, 이후 −로 밀림.
  4. 마지막 덧셈의 참값 0.89999999999999993894…는 0.9의 저장값보다 아래 눈금에 더 가까워(2.78e-17 vs 8.33e-17) 0.8999999999999999로 반올림. 0.9의 저장값과 정확히 1 ULP(1.11×10⁻¹⁶) 차이.
  5. 이 차이는 계산 오류가 아니라 저장 방식의 노이즈. main.py의 decide()는 |차이| < ε(10⁻⁹)이면 UNDECIDED로 신고하고, expected와 다르므로 규칙상 FAIL로 집계 — 의도된 동작.

2.두들 애니메이션 — 여섯 장면

아래 번호나 ← → 키로 장면을 넘기면서 보면 됨.

#1사건: X 필터 점수가 이상하다

size_5_1의 입력은 대각선 9칸이 1.0인 X 패턴, X 필터는 같은 자리가 0.1. 그러니 MAC 점수는 0.1을 9번 더한 값이 된다.

Cross 점수: 0.9

X 점수: 0.8999999999999999

판정: UNDECIDED → FAIL

0.1 × 9 = 0.9 아니었나…?
계산기는 맞고, 저장이 문제였다.

#2컴퓨터는 2진수로만 센다

0.1을 2진수로 바꾸려면 계속 2를 곱하며 정수부를 떼어낸다. 그런데 이 과정이 영원히 끝나지 않는다.

  1. 0.1 × 2 = 0.20
  2. 0.2 × 2 = 0.40
  3. 0.4 × 2 = 0.80
  4. 0.8 × 2 = 1.611을 떼고 0.6
  5. 0.6 × 2 = 1.211을 떼고 0.2
  6. 0.2 × 2 = 0.40← 어? 0.2로 되돌아왔다!

0.2로 돌아온 순간부터 같은 계산이 무한히 반복된다:

0.1(10) = 0.0001100110011001100…(2)

우리가 1/3을 십진수로 0.3333…밖에 못 쓰는 것과 똑같다. 1/10은 2진수의 세계에서 무한소수다.

#3서랍은 53칸뿐

float(IEEE 754 배정밀도)가 소수를 담는 서랍(가수부)은 딱 53비트. 무한히 이어지는 1100…을 53칸에서 잘라내고 반올림한다.

그래서 float 안에 실제로 저장된 값은 0.1이 아니라:

0.100000000000000005551115123125…
= 3602879701896397 / 255

0.1보다 +5.55×10⁻¹⁸ 만큼 크다. 시작부터 이미 어긋나 있다.

#4덧셈할 때마다 또 반올림

float 덧셈은 더하고 → 다시 53비트로 반올림의 반복. 아래는 main.py의 mac()이 실제로 밟은 9단계다 (0인 16칸은 생략).

단계(i,j)파이썬 출력(repr)실제 저장값오차 드리프트

오차가 +쪽으로 부풀다가(3단계) 반올림이 끌어내려 0.5에서 정확히 0, 이후 −쪽으로 밀리며 끝내 0.9보다 한 눈금 아래에 도착한다.

#5눈금 위의 착지

float가 표현할 수 있는 수는 눈금(간격 1 ULP = 1.11×10⁻¹⁶)뿐. 마지막 덧셈의 참값은 눈금 사이에 떨어지고, 더 가까운 눈금으로 반올림된다.

그래서 최종 합은 0.8999999999999999. 한편 코드에 적은 0.9도 사실은 위 눈금 0.90000000000000002…에 저장된다. 둘은 딱 1 ULP 차이.

#6그래서, 판정하지 않기로 했다

1.1×10⁻¹⁶은 계산 오류가 아니라 저장 방식이 만든 노이즈. 이런 차이로 승부를 가르면 사실상 동전 던지기다. main.py의 대응:

EPSILON = 1e-9

def decide(score_a, score_b, label_a, label_b):
    # 노이즈 수준의 차이는 승패로 인정하지 않는다
    if abs(score_a - score_b) < EPSILON:
        return UNDECIDED
    return label_a if score_a > score_b else label_b

|Cross − X| = |0.9 − 0.8999999999999999| = 1.11×10⁻¹⁶ < ε(10⁻⁹)

UNDECIDED — 판정 보류

size_5_1의 FAIL은 버그의 흔적이 아니라, 부동소수점의 한계를 알고 정직하게 신고한 흔적이다.

3.float_trace.py — 추적 스크립트

main.py의 mac()과 같은 행 우선 순서로 곱-누적하며, 매 단계 float에 실제로 저장된 값(Decimal 전개)과 이론값(Fraction)의 차이를 출력함.

"""size_5_1 × X 필터 MAC이 0.8999999999999999가 되는 과정 추적.

main.py의 mac()과 같은 순서(행 우선)로 곱-누적하면서,
매 단계 float에 '실제로 저장된 값'(십진 전개)과 이론값의 차이를 로그로 출력.
"""
import json
import math
import os
from decimal import Decimal
from fractions import Fraction

BASE_DIR = os.path.dirname(os.path.abspath(__file__))
DATA_PATH = os.path.join(BASE_DIR, '..', '..', 'codyssey-e1-3', 'data.json')


def exact(value, digits=22):
    """float에 실제로 저장된 값을 십진수로 그대로 전개한다."""
    return str(Decimal(value))[:digits + 2]


def main():
    with open(DATA_PATH, 'r', encoding='utf-8') as f:
        data = json.load(f)
    pattern = data['patterns']['size_5_1']['input']
    x_filter = data['filters']['size_5']['x']

    print('=' * 100)
    print('size_5_1 패턴 × X 필터 MAC 추적 (main.py mac()과 같은 행 우선 순서)')
    print('=' * 100)
    print()
    print('[0] 재료 확인: 0.1은 float에 어떻게 저장되나')
    print(f'    입력한 값        : 0.1')
    print(f'    실제 저장된 값   : {exact(0.1, 30)}...')
    print(f'    분수로 정확히    : {Fraction(0.1)}')
    print(f'                      = 3602879701896397 / 2^55  (0.1보다 5.55e-18 큼)')
    print(f'    2진수 전개       : 0.0001100110011001100... (1100 무한 반복 → 53비트에서 반올림)')
    print()
    print('[1] 곱-누적 로그 (곱이 0인 16칸은 합을 바꾸지 않으므로 생략)')
    print()
    header = (f"{'단계':>4} {'(i,j)':>6} {'p×f':>8} "
              f"{'repr(누적합) — 파이썬이 출력하는 값':<24} "
              f"{'float에 실제 저장된 값':<26} {'이론값':>6} {'오차':>12}")
    print(header)
    print('-' * 100)

    total = 0.0
    step = 0
    for i, (row_p, row_f) in enumerate(zip(pattern, x_filter)):
        for j, (p, fv) in enumerate(zip(row_p, row_f)):
            if p * fv == 0.0:
                continue
            step += 1
            total += p * fv
            ideal = Fraction(1, 10) * step
            err = float(Fraction(total) - ideal)
            print(f'{step:>4} ({i},{j})  {p:g}×{fv:g}  '
                  f'{total!r:<26} {exact(total):<28} '
                  f'{float(ideal):>6.1f} {err:>+12.2e}')

    print('-' * 100)
    print()
    print('[2] 마지막 덧셈 확대: 8번째 합 + 0.1 이 왜 0.9에 못 미치나')
    s8 = 0.0
    for _ in range(8):
        s8 += 0.1
    stored_01 = Fraction(0.1)
    exact_sum = Fraction(s8) + stored_01          # 반올림 전의 참값
    print(f'    8단계 합(저장값)      : {exact(s8)}')
    print(f'    + 저장된 0.1          : {exact(0.1)}')
    print(f'    = 반올림 전 참값      : '
          f'{str(Decimal(exact_sum.numerator) / Decimal(exact_sum.denominator))[:24]}')
    lo, hi = 0.8999999999999999, 0.9
    print(f'    이 참값 근처의 float 눈금 (간격 = 1 ULP = {math.ulp(0.9):.2e}):')
    print(f'      아래 눈금: {exact(lo)}  ← 참값과의 거리 {float(Fraction(exact_sum) - Fraction(lo)):.3e}')
    print(f'      위   눈금: {exact(hi)}  ← 참값과의 거리 {float(Fraction(hi) - Fraction(exact_sum)):.3e}')
    print(f'    → 참값이 아래 눈금에 더 가까워서 {lo!r} 로 반올림됨')
    print()
    print('[3] 판정에 미치는 영향')
    cross, x = 0.9, s8 + 0.1
    print(f'    Cross 점수: {cross!r}   (실제 저장값 {exact(cross)})')
    print(f'    X     점수: {x!r}   (실제 저장값 {exact(x)})')
    print(f'    x == 0.9        → {x == 0.9}')
    print(f'    |Cross − X|     → {abs(cross - x):.3e}')
    print(f'    epsilon(1e-9)   → {abs(cross - x):.3e} < 1e-9 → UNDECIDED (판정하지 않음)')


if __name__ == '__main__':
    main()
